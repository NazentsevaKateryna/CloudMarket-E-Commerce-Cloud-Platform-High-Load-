### 1. Шар і правило залежностей

У проєкті реалізовано 4 ізольовані шари за Clean Architecture (Роберт Мартін):
* **`src/Domain`:** містить доменну сутність `Order`, Value Object `Money`, виняток `OrderDomainException` та інтерфейс-порт `IOrderRepository`. Шар не імпортує зовнішніх бібліотек, ORM чи фреймворків.
* **`src/Application`:** сценарій використання `CreateOrderUseCase`, DTO (`CreateOrderCommand`, `OrderResultDTO`) та вихідний порт `IPaymentGatewayPort`. Залежить виключно від `Domain`.
* **`src/Infrastructure`:** конкретні реалізації адаптерів: `InMemoryOrderRepository` (імплементує `IOrderRepository`) та `FakePaymentGatewayAdapter` (імплементує `IPaymentGatewayPort`).
* **`src/WebAPI`:** `OrderController` та композиційний корінь `ServiceContainer`. Залежить від абстракцій `Application` та підключає реалізації з `Infrastructure`.

**Підтвердження відсутності посилань назовні з Domain:**  
Усі файли в директорії `src/Domain` містять імпорти лише сусідніх файлів свого шару. Жодного імпорту з `Infrastructure`, `WebAPI`, сторонніх HTTP-бібліотек чи баз даних немає.

### 2. Сценарій використання (Use Case)

* **Ім'я сценарію:** `CreateOrderUseCase` (`src/Application/UseCases/CreateOrderUseCase.ts`).
* **Порти в конструкторі:**
  1. `orderRepository: IOrderRepository` (збереження сутності).
  2. `paymentGateway: IPaymentGatewayPort` (проведення оплати замовлення).
* **Доменні правила валідації:**
  1. Замовлення повинно містити щонайменше 1 позицію товару (`items.length > 0`).
  2. Довжина адреси доставки має бути не менше 5 символів.
  3. Сума замовлення не може бути від'ємною (контролюється `Money`).
  4. При невдалому виклику платіжного порту генерується `OrderDomainException`, і запис у сховище скасовується.

### 3. Композиційний корінь (Composition Root)

| Абстракція / Порт | Конкретна реалізація | Життєвий цикл | Чому саме цей цикл |
| :--- | :--- | :--- | :--- |
| `IOrderRepository` | `InMemoryOrderRepository` | **Singleton** | Єдине сховище `Map` у пам'яті на рівні процесу для збереження стану між викликами тестових сценаріїв без реальної СУБД. |

### 5. Контрольні запитання для захисту

1. **Чому шар Domain не повинен мати посилань на шар Infrastructure?**  
   Domain містить бізнес-правила системи, які є найбільш стабільною і цінною частиною продукту. За правилом залежностей Clean Architecture внутрішній шар нічого не знає про зовнішні деталі. Якщо Domain залежить від Infrastructure, зміна СУБД, ORM чи зовнішніх API змусить модифікувати бізнес-правила, а також унеможливить тестування ядра без підняття важкої інфраструктури.

2. **Чим відрізняються життєві цикли Transient, Scoped та Singleton в DI-контейнерах?**  
   * **Transient:** новий екземпляр створюється під час кожного запиту з контейнера; використовується для невеликих сервісів без збереження стану.  
   * **Scoped:** створюється один спільний екземпляр на весь життєвий цикл одного запиту/контексту (наприклад, один об'єкт на HTTP-запит або транзакцію).  
   * **Singleton:** створюється рівно один екземпляр на весь життєвий цикл програми (процесу); використовується для сховищ кешу, конфігурацій чи сервісів без змінного стану користувача.

3. **Як використання інтерфейсів репозиторіїв дозволяє тестувати сценарії ізольовано від бази даних?**  
   Сценарій використання знає лише інтерфейс `IOrderRepository`, а не реальну SQL/NoSQL базу. Під час тестування в конструктор сценарію передається mock-заглушка або фейкова реалізація в пам'яті (`InMemoryOrderRepository`), що перехоплює виклики `save` та `findById`. Це дає змогу проводити тести за частки секунди без мережевих сокетів, транзакцій і попереднього наповнення бази даних.
