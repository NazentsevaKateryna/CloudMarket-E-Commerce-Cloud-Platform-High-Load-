# ADR-0001. Вибір базового архітектурного стилю для платформи CloudMarket

## Статус
Accepted

## Контекст
Розроблювана система E-Commerce Cloud Platform має вимоги до високої швидкості виходу на ринок (Time-to-Market для MVP) за умов роботи невеликої команди інженерів (4-5 розробників). При цьому бізнес вимагає високої модульності, щоб мати змогу в майбутньому виділяти високонавантажені частини (наприклад, Catalog або Order Processing) в окремі автономні сервіси без повного переписування кодової бази. Створення повноцінної мікросервісної інфраструктури на ранній стадії створить надмірне операційне навантаження на команду та ускладнить узгодження доменної моделі.

## Рішення
Обрано архітектурний стиль **Модульний Моноліт (Modular Monolith)** із застосуванням принципів **Clean Architecture** (Роберт Мартін) усередині кожного окремого модуля.

Усі функціональні модулі платформи (`Catalog`, `Order`, `Inventory`, `Payment`, `Notification`) розміщуються в єдиному репозиторії та компілюються/розгортаються як єдиний артефакт. Модулі мають власні ізольовані доменні моделі, шари бізнес-логіки та доступ до даних. Будь-яка взаємодія між модулями відбувається виключно через типізовані публічні контракти (інтерфейси/фасади) або внутрішню шину асинхронних подій. Пряме звернення до чужих внутрішніх класів або таблиць БД суворо заборонено.

## Розглянуті альтернативи
- **Повноцінна мікросервісна архітектура (Microservices):**
  - *Мінуси:* висока складність оркестрації (Kubernetes, Service Mesh), затримки мережі при міжсервісних викликах, складність забезпечення узгодженості даних (Distributed Transactions / Saga Pattern). Відхилено для стадії запуску.
- **Класичний шаруватий моноліт (Layered 3-Tier Monolith):**
  - *Мінуси:* швидка деградація архітектурних меж, високе зачеплення (coupling), високий ризик виникнення неконтрольованих залежностей («Big Ball of Mud»), надзвичайна складність подальшого розпилу системи. Відхилено.

## Наслідки
- **Позитивні:**
  - Швидке розгортання та локальне налагодження в межах одного середовища.
  - Відсутність накладних витрат на мережеву серіалізацію/десеріалізацію між доменами.
  - Чітка ізоляція коду, що дозволяє за необхідності безболісно винести будь-який модуль в окремий мікросервіс у майбутньому.
- **Негативні / Компроміси (Trade-offs):**
  - Необхідність суворого налаштування лінтерів архітектури (ArchUnit/Dependency-cruiser) та дисципліни Code Review для збереження меж.
  - Помилка (memory leak / fatal error) в одному модулі може вплинути на весь монолітний процес.
