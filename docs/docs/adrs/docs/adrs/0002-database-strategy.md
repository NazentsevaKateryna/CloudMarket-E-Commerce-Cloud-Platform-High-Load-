# ADR-0002. Вибір стратегії баз даних та персистентності

## Статус
Accepted

## Контекст
Маркетплейс CloudMarket оперує критично важливими фінансовими та обліковими даними (замовлення, транзакції, платежі, залишки на складах), які вимагають суворої узгодженості за стандартом ACID. Водночас модуль каталогу товарів має специфіку з переважанням операцій читання (відношення Read/Write $\approx 9:1$), гнучкими атрибутами товарів (електроніка, одяг, книги) та піковими сплесками запитів.

## Рішення
Застосувати стратегію поліглотного збереження (**Hybrid Polyglot Persistence**):
1. **Основна реляційна СУБД — PostgreSQL:** єдине джерело істини (Single Source of Truth) для замовлень, платежів, складського обліку та користувачів. Для товарів із динамічними характеристиками використовується підтримка колонок типу `JSONB` з GIN-індексацією.
2. **Розподілений кеш у пам'яті — Redis:** кешування популярних карток товарів, сторінок каталогу, лічильників переглядів та збереження кошиків неавторизованих користувачів.

## Розглянуті альтернативи
- **Повністю документоорієнтована NoSQL СУБД (MongoDB):**
  - *Мінуси:* складність забезпечення суворої узгодженості та безпечного блокування залишків (Pessimistic / Optimistic Locking) у сценаріях одночасного викупу одного товару кількома покупцями; відсутність природних зв'язків між сутностями. Відхилено для фінансового ядра.
- **Єдина СУБД MySQL без додаткового кешування:**
  - *Мінуси:* пряме навантаження на диск під час пікових розпродажів спричинить суттєву деградацію Time Behaviour; менш зручні інструменти для роботи з неструктурованими JSON-даними порівняно з PostgreSQL. Відхилено.

## Наслідки
- **Позитивні:**
  - Гарантія надійності фінансових операцій та запобігання ситуаціям оверселінгу (продажу відсутнього товару).
  - Зниження середнього часу відповіді при читанні каталогу до $\le 10\text{ ms}$ завдяки Redis.
  - Гнучкість структури каталогу товарів через PostgreSQL `JSONB`.
- **Негативні / Компроміси (Trade-offs):**
  - Необхідність реалізації надійного патерну інвалідації кешу (Cache Invalidation) при зміні залишків або цін товарів.
  - Збільшення витрат на підтримку двох різних систем баз даних у виробничому середовищі.
