# ADR-0003. Вибір архітектури автентифікації та контролю доступу

## Статус
Accepted

## Контекст
Платформа передбачає розгалужену систему ролей користувачів: роздрібні клієнти, мерчанти магазинів, контент-модератори, оператори фінансового відділу та системні адміністратори. Необхідно впровадити безпечну, масштабовану та відкриту для інтеграцій систему автентифікації, яка підтримує Web SPA, нативні мобільні застосунки та зовнішні API-інтеграції для мерчантів.

## Рішення
Впровадити архітектуру на основі стандарту **OAuth 2.0 / OpenID Connect (OIDC)** із застосуванням комбінованих JSON Web Tokens (JWT):
- **Access Token:** короткоживучий токен (строк дії 15 хв), підписаний асиметричним алгоритмом RS256, що передається в заголовку `Authorization: Bearer` і містить claims про ідентифікатор користувача та його роль (Role-Based Access Control — RBAC).
- **Refresh Token:** довгоживучий токен (строк дії 14 днів), який видається за механізмом Refresh Token Rotation, зберігається в захищених cookie-файлах з прапорцями `HttpOnly; Secure; SameSite=Strict`, а його унікальний `JTI` фіксується в Redis для підтримки механізму миттєвого відкликання сесії (Revocation/Blacklist).

## Розглянуті альтернативи
- **Традиційні серверні сесії (Server-Side Stateful Sessions):**
  - *Мінуси:* прив'язка до стану сервера або необхідність постійних запитів до центральної сесійної бази при кожному зверненні до API, що знижує загальну масштабованість бекенду та додає мережеві накладні витрати. Відхилено.
- **Reference (Opaque) Tokens:**
  - *Мінуси:* вимагають обов'язкового мережевого звернення до сервера авторизації (Introspection API) при кожному внутрішньому запиті, що створює пляшкове горло для High-Load платформи. Відхилено.

## Наслідки
- **Позитивні:**
  - Автономна валідація запитів модулями системи за відкритим публічним ключем (Public Key) без звернення до БД чи сервісу авторизації.
  - Висока сумісність із мобільними клієнтами та сторонніми сервісами.
  - Захист від XSS (завдяки `HttpOnly` для refresh) та мінімізація вікна атаки при витоку Access Token.
- **Негативні / Компроміси (Trade-offs):**
  - Неможливість миттєво анулювати вкрадений Access Token до завершення строку його дії (15 хв) без створення додаткових глобальних чорних списків.
  - Необхідність суворого регламенту ротації та збереження приватних ключів шифрування (Key Management Service).
